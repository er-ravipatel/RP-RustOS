# P7 read-only header and synchronous-vector prototype

2026-11-01. Extended the isolated emulator adapter, not the production BSP. [Assembly](../tools/entry-harness/handoff.S), [runner](../tools/test_entry_handoff.py), [retained evidence](evidence/p7-entry-header-tests.json).

The EL2 prototype checks pointer alignment, low/upper bounds, header extent and kernel-budget disjointness before header loads. It checks big-endian magic, total size capped at 2 MiB, complete extent and kernel overlap, compatible FDT versions, map alignment/room for a reservation terminator, structure alignment/length and block ordering/extent. It performs no reservation-map iteration, token parsing, board/RAM verification or stack setup. Passing this checkpoint authorizes none of those later writes.

Installed EL2 vectors are 2 KiB aligned. Every 128-byte slot contains one branch to the register-only fault handler and NOP padding. The runner checks all 16 encoded branch targets/padding against ELF symbols. The handler captures ESR_EL2, ELR_EL2 and FAR_EL2 into registers, sets a fault marker and parks without returning. The complete code before the literal pool is decoded and checked for allowed instructions with no stores, calls or SP/WSP operands. These compiled-code checks do not replace runtime write tracing.

All 15 emulator scenarios pass: prior normal/EL1/cache cases; a readable valid header; invalid magic, oversized total, invalid version, structure alignment and strings extent; misaligned, kernel-overlapping, ceiling-crossing, zero and wrapping pointer values; and an injected BRK synchronous exception. Every result requires the expected marker, level/PSTATE and exact linked park loop. The BRK case additionally requires ESR exception class 0x3c. Invalid pointers are rejected before loads by the intended bounds checks.

The valid header fixture intentionally does not contain a validated tree; this prevents confusing header acceptance with DTB acceptance. The BRK case tests synchronous routing but is not an unreadable-memory data-abort test. The raspi3b model may return data for some unassigned physical addresses, so no data-abort coverage is inferred. Only CPU 0 is observed. A review found and closed a potential pointer-addition wrap path by checking the pointer ceiling before adding the header length; the wrapping-pointer case now verifies explicit rejection.

No production kernel, safe writable stack, memory allocator, UART, pinned firmware or physical Pi boot was exercised. M1 remains unchanged. Next: extend header boundary cases and reservation-map checks, add a controlled data-abort fixture if the harness can establish it without weakening the production policy, then implement bounded tree safety passes. Exact production CPU masks and complete register liveness remain open.
