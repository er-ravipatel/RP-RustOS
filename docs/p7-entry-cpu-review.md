# P7 CPU guard, register readback and panic verification

2026-11-01. D21 implementation remains in progress; no production Pi image is generated by these experiments.

## Completed

The [CPU guards](../tools/entry-harness/cpu-guards.S) are now inserted immediately after EL2/cache-state checks and before the first DTB preflight load in both the transition and Rust-call experiments. They check Cortex-A53 identity, all MPIDR affinity fields, and inherited MMU/cache/endianness state. Secondary affinity parks without stack setup. Production still needs its own entry wiring.

The [transition](../tools/entry-harness/el1-transition.S) reads back HCR_EL2, CPTR_EL2, HSTR_EL2, CNTHCTL_EL2, CNTVOFF_EL2, SPSR_EL2, SP_EL1, VBAR_EL1 and ELR_EL2 before ERET, and compares the virtual identity registers with the physical identity registers. EL1 checks SCTLR_EL1, CPACR_EL1, DAIF, stack top and disabled timer controls, then tests real SIMD execution.

[Fourteen CPU cases passed](evidence/p7-entry-cpu-guards.json): normal, deliberate EL1 fault, invalid RAM, wrong CPU identity, accepted A53 variant/revision, ignored non-affinity MPIDR flags, rejection/parking for each of Aff0 through Aff3, and modeled MMU/data-cache/instruction-cache/big-endian rejection. The alternate MIDR/MPIDR/control values are injected into the observed-register value used by the guard. They test comparisons and masks, not live MMU/cache switching, alternate physical CPUs or actual secondary-core execution. Rejected cases retain SP=0 and remain at EL2.

[Four real Rust-call cases passed](evidence/p7-entry-rust-panic.json): no pool, valid pool, insufficient pool space, and an explicit Rust panic. The panic invokes Rust panic machinery and the unformatted harness panic handler, then reaches its exact EL1 park with marker 0xface. Its CPU0 writes remain inside the private stack under the same outside-stack watchpoints used for the validator cases. This is a deliberately triggered panic experiment, not proof that every malformed DTB path is panic-free. The harness handler still needs production integration.

## Static stack review remains open

Generated the release AArch64 assembly with rustc 1.88.0 and retained a [frame/call inventory](evidence/p7-entry-stack-inventory.json). Twelve BSP functions were inventoried, with seven external call targets and no indirect branch/call in that assembly. The requested LLVM stack-size option did not emit a stack-size section in this output. Do not interpret absence of metadata as a zero frame.

The main memory validator has a page-probing loop: it computes a target five pages below SP and repeatedly subtracts one page before allocating its remaining frame. Counting only literal stack-subtraction instructions would undercount it. External slice/panic and memory helpers also require review in the final linked artifact. Therefore neither this inventory nor the earlier 21,280-byte observed write extent is a complete static stack bound.

Before production wiring: finish the reachable linked-helper/frame proof within 64 KiB (including panic paths), verify actual multicore behavior and relevant entry-state failures, and retain a production disassembly/write-order audit. Physical Zero 2 W firmware/UART acceptance remains pending separately. M1 and the approved asset lock remain unchanged.

The subsequent [linked stack audit](p7-entry-stack-bound.md) satisfies the stack-bound gate for its four exact test artifacts; production artifacts still require a new audit.
